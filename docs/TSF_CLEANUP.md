# .9後のTSF整理

基点はbd64449（公開済みv0.1.0-tsf-direct.9）、作業ブランチはcodex/tsf-cleanup。
.9の公開ZIP、リリースタグ、DLLは変更しない。整理版はまだリリースしない。

## 整理した箇所

- 成功した置換では失敗診断の取得用DLL関数を呼ばず、失敗メッセージも組み立てない。
  失敗時の元の範囲・差分・挿入UTF-16単位の診断は維持する。
- プロトコル102に必須の文脈取得・診断APIについて、旧版向けのoptional分岐を撤去。
  不完全なDLLは監視開始前に明示的に拒否する。
- 確定文字列・取得文脈の改行正規化を共通化し、編集プロトコル番号も一か所へまとめる。
- 同じOnEndEditの読み取りcookie内で、診断と原文確認のために行っていた対象本文の二重取得を一回にする。
  この局所的な共有は別セッションへ持ち越さない。書き込み直前の原文・文脈の再確認は削除しない。
- 文脈の範囲読み取りを共通化し、文字数上限とUTF-16単位上限の関係を定数として表現。
  公開API・共有構造体の配置・プロトコル102は変更しない。
- TSF専用実験起動で使わなくなったDesktopの生成・UIA編集環境の初期化・終了処理を撤去。
  通常起動のDesktopは手動変換に必要なので維持する。
- 通常起動はExitStackで終了処理を登録し、監視終了時などの例外でも、ショートカット解除・AI実行用executor・編集ワーカー・日本語キー監視の終了処理をすべて試みる。
  実験起動も監視終了の例外でexecutorの終了処理を飛ばさないようにする。

## 維持する条件

原文・参照文脈・範囲・選択・入力先・IME状態による適用判定、次の入力での中止、一度だけのSetText、
結果不明時の停止を維持する。待ち時間、フォールバック、編集の再送は追加しない。
TSF監視専用DLLや手動Win32/UIA経路の実装は削除しない。

## 検証

成功時に診断DLL呼び出しとメッセージ整形を実行しないこと、失敗時に数値診断が残ること、
必須API不足で開始しないこと、監視終了に失敗してもexecutor・編集ワーカー・ホットキーの終了処理を試みることを検証する。
.9と同じ通常経路1,000回・既存境界720回・未知の追加350回・参照文脈内外150回の反復も実行する。
検証DLLは未公開のテスト用パス429を使用し、.9の431は変更していない。

## 結果

- 全体の回帰試験308件成功（297.708秒）。通常経路の文脈取得＋置換1,000/1,000回、境界720回、未知の追加350回、参照文脈内外150回を含む。
- 通常起動の終了処理を追加修正した後、NormalLoopTests・NativeReplyTests・TrialRoutingTestsの19件が成功（0.140秒）。全体実行に未収録だった終了処理試験1件を含み、確認した試験の種類は合計309件。
- 専用入力欄での文脈取得＋置換の往復中央値31.243ms、最大43.832ms。メッセージ処理周期を含むので、実アプリでの速度改善をこの数値から断定しない。
- 別名のローカル配布物dist/kana-rewriter-tsf-cleanup-windows-x64.zipを作成し、両DLL読み込み・CLI起動・ソースと編集DLLの対応を確認した。
- mainへの統合、新リリース公開、既存.9リリースの変更は行っていない。
