# TSF確定通知から自動置換までの検証

検証ブランチ: `codex/tsf-ime-commit-probe`。最初は実験用モードとして作成し、実機確認後に通常起動のオプションへ組み込んだ。

## 通常起動のオプション

`config.toml`で`auto_replace_on_ime_commit = true`に設定するか、通常起動に`--auto-replace-on-ime-commit`を追加して有効にする。既定は無効。`--no-auto-replace-on-ime-commit`で起動時だけ無効にできる。

```cmd
.\.venv\Scripts\python.exe -m kana_rewriter --config config.toml --auto-replace-on-ime-commit
```

通常モードでは入力先の切り替えを追跡する。同じGUIスレッド内で入力欄を切り替えた場合は、UIAの入力欄識別情報を更新して古い通知を捨てる。別のGUIスレッドへ移る場合は、旧監視を解除して新しい監視を登録する。変更前の入力欄で始まった通知や、Enter単独の通知で新しい欄の自動変換を開始しない。

変換中は新しい確定通知を変換待ちキューへ積まず、入力・フォーカスの変化を監視して適用を中止する。手動ショートカットを使うと、待機中の自動変換候補を破棄する。自動変換の監視が停止しても手動ショートカットは利用できる。DLLがない場合や初期化失敗時は、設定を有効にした起動をエラーとして扱い、無効化して起動し直せる。

DLLは既定では`build/tsf-probe/latest.json`の最新ビルドを使う。`tsf_monitor_path`に別のDLLを指定する場合は、設定ファイルの場所を基準に相対パスを解決する。Pythonの直接編集方式と64ビットWindows/Pythonが対象。

### 検出と置換の役割分担

- C++のTSF監視が未確定範囲の開始・終了、取消、未確定属性を追跡し、終了後に文字が残った範囲を確定候補として通知する。範囲の開始時刻は途中の編集でも保持する。
- `kana_rewriter/tsf.py`はDLLとの通信と共通の適用条件を担当する。Enterを伴う、かなを含む候補に限定する条件は自動変換の方針であり、TSFの確定検出とは分ける。`Ctrl+Enter`はIMEの全確定として観測するが、利用者が置換を望まない確定として自動変換の対象外にする。検証用コマンドも同じ通信・条件を使う。
- `auto_ime.py`は入力先と処理の世代を管理する。Pythonでは未確定状態を再構成せず、通知の開始時刻が入力先の変更・前回処理の終了より古い場合に除外する。本文取得と適用では、既存の編集エンジンが本文・カーソル・入力欄の一致を確認する。

通知形式はバージョン3。開始時刻とEnter押下時の修飾キーを追加したため、旧DLLを明示指定している場合は再ビルドが必要。互換性確認は通知バッファを渡す前に行い、不一致なら起動をエラーにする。このワークスペースの最新DLLは再ビルド済み。

`Ctrl+Enter`の判定は、DLLがEnterのキー通知時に取得した修飾キー状態を使う。キーを離した後や通知の遅延で状態が変わっても、押下時の`Ctrl`を失わない。

役割分担の整理後、Windowsで228件のテストが成功。入力先変更前・処理中に開始した範囲の除外、途中の編集でも開始時刻を保持すること、旧DLLの拒否を追加確認した。Ctrl+Enterの抑制を追加した時点ではWindowsで237件のテストが成功した。以下の実IMEによる利用者確認は整理前の実装に対するもの。

2026-10-14、通常起動の有効化オプションで、Chrome/Webメモのモデル変換、入力欄・アプリを切り替えた後の追従、未確定での停止・Escape取消の試験を依頼し、利用者から「正常に動作しています」と確認を得た。

## 現時点の結果

このPCの64ビットWindows上で、以下の合成試験が成功した。

- 別プロセスで動作する非表示のTSF対応アプリへ、対象スレッド限定の監視DLLを接続。
- 既存TSFマネージャー・入力コンテキストへの監視登録。
- 本物のTSF編集セッションで作った未確定範囲の開始・終了を観測。
- 合成した確定で「さんぽ」を取得し、合成した空文字への取消では候補を生成しない。
- TSFから取得した文字列を、既存のPython編集エンジンと固定変換結果へ渡し、別プロセスの標準Editに「散歩」を書き込み、本文とカーソルを確認。
- 同じ対象への登録・解除を繰り返し、重複した監視ホストを拒否。
- 同一HWNDでもUIAの入力欄が変わった場合、取得を拒否。

非表示アプリの試験では、前景・入力監視の状態をモックしている。TSF編集通知、DLL接続、標準Editの置換メッセージは実際に実行している。試験用アプリがTSF編集セッションを合成しており、実際のMicrosoft IMEによる確定・Enterキー通知を再現した試験ではない。

2026-10-14、利用者のChrome/Webメモで実IMEによるEnter確定後の固定結果置換が成功した。受け取ったログには、未確定範囲`active=1`、Enter`key=13`、範囲終了`active=0`、3文字の`commit_candidate`、`converting`、`applied`が順に記録されている。利用者からも置換されたとの報告があり、終了時は`clean_detach=true`だった。

固定結果試験に続き、同じChrome/Webメモでモデルを使った自動置換も成功した。空の入力欄の「きょうはいいてんきです」のEnter確定、未確定のまま数秒停止、Escape取消の試験を依頼し、利用者から「うまく行っています。確定をした場合にのみ変換が走ります」と報告を受けた。

部分確定・マウス確定、メモ帳・VS Codeの実IME操作は別途確認が必要。Chromeでの成功から他アプリの互換性は推定しない。固定結果試験ログ末尾の編集ワーカー`KeyboardInterrupt`表示は、ワーカーがCtrl+Cを受け取った場合も通常の後始末へ進むよう修正した。

モデルを使った実機試験でも、`commit_candidate`から`converting`、`unchanged`まで進んだ。手元の同じ設定で単体推論したところ、文脈なしの「さんぽ」は原文のまま返った。一方、「きょうはいいてんきです」は「今日はいい天気です」、「天気がいいので、」という左文脈の「さんぽ」は「散歩」に変換された。モデル試験では、このように実際に出力が変わる入力を使う。

## ビルド

64ビットWindows/Pythonが必要。現在のワークスペースにあるllvm-mingwを使う場合:

```powershell
.\scripts\build_tsf_probe.ps1
```

別の64ビットMinGW/llvm-mingw環境では`-Compiler <clang++.exeのパス>`を指定する。ワークスペースのコンパイラーがない場合は、Visual StudioのC++開発環境とCMakeでもビルドできる構成にしている。この環境で実際に確認したビルドはllvm-mingw。

`build/tsf-probe/kana-tsf-probe-<ビルド時刻>.dll`と`tsf-probe-fixture.exe`を生成する。`latest.json`で最新DLLを選ぶため、旧DLLが対象アプリに残っていても再ビルドできる。IMEのインストールや登録、既定IMEの変更は行わない。

## 最初に試すコマンド

通常起動中のkana-rewriterを終了してから実行する。実行後5秒以内に、試す入力欄へフォーカスを移す。監視対象は、そのスレッドに固定する。自動置換時は開始時のUIA入力欄にも固定し、同じアプリ内でも別欄へ移動した場合は中止する。

監視だけ（モデルを読み込まず、文字を書き換えない）:

```cmd
.\.venv\Scripts\python.exe -m kana_rewriter.tsf_probe --seconds 60
```

AIなしの自動置換試験:

```cmd
.\.venv\Scripts\python.exe -m kana_rewriter.tsf_probe --auto-replace --fixed-source "さんぽ" --fixed-result "散歩" --seconds 60
```

「さんぽ」をかなのままEnterで確定する。確定候補が「さんぽ」と完全一致した場合だけ「散歩」へ置換する。モデルの精度や応答時間を、確定検知の成否と混同しないための試験。

固定結果で動作した後、モデルを使う試験:

```cmd
.\.venv\Scripts\python.exe -m kana_rewriter.tsf_probe --config config.toml --auto-replace --seconds 60
```

モデルの読み込みが完了してから、フォーカス移動の5秒を数える。`--debug`は既存編集処理の本文・文脈ログも表示する。終了は監視時間の経過、または端末のCtrl+C。

空の入力欄に「きょうはいいてんきです」をかなのまま入力し、Enterで確定する。「さんぽ」単独は現在のモデルが原文のまま返す場合があり、`unchanged`は検知失敗ではない。

## ログの読み方

| event | 意味 |
|---|---|
| `started` | 指定スレッドへのフック設置。TSF監視登録の成功とは別 |
| `attached` | 対象内のTSFマネージャー監視を登録 |
| `context` / `hr=0x00000000` | 入力コンテキストへ編集監視を登録 |
| `editing` / `active=1`等 | 未確定範囲が存在する編集通知 |
| `commit_candidate` | 観測済みの未確定範囲が終了し、範囲に文字列が残っている |
| `canceled_or_empty` | Escapeの観測、または終了範囲の文字列が空 |
| `converting` | 確定候補・Enter・本文の一致を確認し、変換開始 |
| `applied` | 既存編集処理で置換・反映確認に成功 |
| `unchanged` | 変換結果が原文と同じ |
| `skipped` / `enter_not_observed` | 新しいEnter操作を観測できないため自動置換しない |
| `unsupported` | 部分・重複確定、取得上限、属性不明など。自動置換の根拠にしない |
| `aborted` | 本文不一致、入力欄変更、推論中の入力などで置換を中止 |
| `error` / `failed` | 接続・読み取り・変換などの失敗 |
| `stopped` / `clean_detach=true` | 対象内の監視解除を確認 |

`key`はTSFのKeyTraceで観測した仮想キー。Enterは13。文字列は通常ログに出さず、文字数を出す。確定候補とEnter操作の鮮度を確認する。

`commit_candidate`単体を「確定の証明」と扱わない。取消で元の文字が復元される場合などがあるため、試作の自動置換には新しいEnter観測と実際の本文・カーソルの一致も必要とする。Enterだけを根拠にタイマーで置換する方式ではない。

## 試作の制限

- 通常権限の64ビットアプリを最初の対象とする。32ビット、ARM64、管理者権限、保護されたプロセス、アプリコンテナーの互換性は未検証。
- 自動置換はEnterを伴う、観測済みの範囲全体の終了のみ。文節の部分確定・マウス確定等はまず観測対象とし、自動置換を保証しない。
- 自動置換にはPythonの直接編集方式を使用する。パスワード・読み取り専用等は既存の編集処理でも拒否する。検証は通常の編集欄で行う。
- TSFからの通知後、Chromeなどの本文反映を待つため読み取りだけを最大0.7秒再試行する。時間経過を確定の根拠にはせず、文字列・カーソルの一致を確認する。
- 推論中に編集通知・キー操作・コンテキスト変更があれば中止する。通知欠落も中止条件。書き込みは再送しない。
- 対象アプリ内では推論しない。DLLはTSF読み取りと共有メモリへの通知のみを行う。
- COMコールバックの参照先を失わないよう、DLLのモジュールは対象プロセスの終了まで固定する。監視停止時には監視解除、非表示制御ウィンドウ、共有メモリ等を解放するが、DLL自体はプロセス終了まで残る。解除失敗・通知欠落では自動変換を停止する。

## 自動試験

```cmd
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -p test_tsf_probe.py -v
```

実IME試験では、まずChrome/Webメモで固定結果を確認し、次にメモ帳・VS Codeで同じ操作を行う。「未確定のまま停止」「Escape取消」「入力欄変更」「推論中の追加入力」でも自動置換しないかを確認する。
