# 入力仕様・編集処理の詳細

導入と起動は[README](../README.md)、内部構造は[アーキテクチャ](ARCHITECTURE.md)を参照してください。以下のK/Jは既定の機能名です。実際のキーは設定ファイルに従います。

## 変換範囲とカーソル

ショートカットの主キーは英字・数字、F1〜F24（予約キーF12を除く）、Space・Enter・Tab・Escape・Backspace・Insert・Delete・Home・End・PageUp・PageDown・Left・Up・Right・Down・半角全角に対応します。修飾キーはCtrl・Alt・Shift・Winです。ファンクションキーと半角全角は単独指定も可能です。半角全角の別名は`半角/全角`・`半角／全角`・`HankakuZenkaku`・`ZenkakuHankaku`。別名で指定しても設定内の重複は検出します。

利用者環境では、GetAsyncKeyStateによる仮想キー照会に加えて、低レベルキーボードフックによる確認でもキー解放待ちが約2秒で中止しました。このため半角全角の解放は、受付プロセスの専用スレッドとメッセージ専用ウィンドウで[Windows Raw Input](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input)を受け、物理スキャンコードSC029のmake/breakを確認します。RIDEV_INPUTSINKでバックグラウンド受信し、仮想キーのGetAsyncKeyStateに依存しません。同じキーボードのRaw Inputに解放の指標がある場合のみ、そのキーボードの押下状態を解除します。拡張キーやデバイス情報のない通知は解放の根拠にしません。他のキーや入力本文は保存せず、通常のキーイベントを遮断しません。終了時にはRaw Input登録とウィンドウを解除します。

スキャンコードは[MicrosoftのRAWKEYBOARDサンプル](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawkeyboard)に従い、上位のbreakビットを除いて比較します。例えば0x29と0xA9は同じキーとして扱い、解放はRI_KEY_BREAK、またはRaw Input内のMessageがWM_KEYUP / WM_SYSKEYUPであることで判定します。利用者ログにはSC029・Flags=0・VK=0xF4・Message=WM_KEYUPという通知があり、Flagsだけを見た従来実装が解放を押下として数えていました。通常のウィンドウメッセージを別途受信する方式ではなく、同じRaw Input通知内の指標を補完します。スキャンコードが0の場合は、半角全角に関係する仮想キーだけMapVirtualKeyWで補完し、結果がSC029になった場合だけ採用します。拡張キーや別の物理キーでは解除しません。

Raw Input取得や監視スレッドに異常があれば編集を中止します。`--debug`では半角全角に関係する通知の元のscan・flags・vk・message・deviceと採否、押下・解放の累積検出回数と現在の押下状態を表示します。自動試験では実際の登録・解除、Flags=0とWM_KEYUP / WM_SYSKEYUPの組み合わせ、0xA9の解放や空スキャンコード、仮想キーや通常メッセージが変わった場合、別キーボードの解放、不完全な通知、取得失敗を確認しています。実機での半角全角キーの通知は利用者環境で確認する必要があります。

直接編集では取得・推論をキー押下時に開始し、適用前に物理解放を最大2秒待ちます。仮想キーの0xF3/0xF4は編集ワーカーのGetAsyncKeyStateによる待機対象から外します。通常の修飾キー・入力先・本文・位置・操作監視の確認は維持します。監視停止や物理入力を確認できない場合は中止し、解除確認を省略して入力することはありません。実機のIME・キー配送との相性は別途確認が必要です。

Kは未選択の状態で使います。既定では、カーソルから左へ漢字・カタカナまたは句点「。」まで走査します。「、」「?」「!」や空白・英数字は区切りにしません。本文の先頭と改行でも止めます。画面上の折り返しには左右されません。範囲内にかながなければ中止します。助詞の判定はないため、`私はきょう│`では`はきょう`が対象です。

カーソル直前が `。 、 ？ ? ！ ! , . ， ．` の場合は、連続するこれらの記号を飛ばして、その左から同じ走査を行います。これは区切り文字の設定とは独立しています。記号は保持します。例: `今日はいい天気だ。さんぽでもしようか。│` → `今日はいい天気だ。散歩でもしようか。`。

変換による文字数の変化を考慮してカーソルを復元します。記号の直後から実行した場合は記号の直後に戻します。Win32はUTF-16の選択位置を使います。UIAは条件が合うChromiumのEdit入力欄では文字入力と右矢印を一括送信し、それ以外では確認済みのTextRange.Selectを使います。Jでは変換範囲の末尾に置きます。UIAの文字単位と本文を対応づけられない位置では中止します。

K・J・`--text`では、専用モデルに渡せる連続したかなの部分を順に変換します。漢字・句読点・空白・改行・英数字はそのまま保持します。新方式のJでは選択範囲外の文脈も取得します。単語や助詞の判定は行いません。

入力欄の本文から対象前後を取得します。既定のzenzには左右それぞれ最大64文字の文脈を渡します。jinenには左文脈だけを渡します。置換対象以外の文字はモデルに生成させず、そのまま保持します。

取得時は選択を動かしません。本文取得・推論待機・選択反映・文字送信直前・カーソル復元の全段階で、マウス移動やキーの解放だけでは中止しません。本文・選択位置・入力先を再確認して適用を判断します。置換開始後はキー押下・クリック・ホイール操作を検出すると中止し、マウスボタンを押したままの操作も対象外です。UIAでは選択反映を確認してから変換結果を一度だけ送信し、本文を再取得して結果を確認します。確認に失敗した場合は再送しません。中止後に選択範囲が残った場合は解除するか、選び直して再実行してください。

クリップボード不使用版ではショートカットを押した時点で本文取得と推論を始めます。適用直前に主キーと修飾キーの解放を確認し、まだ押されていれば最大2秒待ちます。通常は推論中にキーを離すため、この待ちはほぼ発生しません。キー解放後に本文・位置・入力先を再確認してから編集します。

ショートカット受信・推論完了は通知で待機を解除し、20ms周期の確認待ちをなくしています。編集ワーカー・UIA・入力監視は起動完了前に準備します。UIAの重複する範囲取得を減らし、直近で確認したカーソル位置から範囲を作ります。一致確認と空行境界用の代替処理は維持します。

クリップボード不使用版の操作監視は、専用スレッドのWindows入力フックでイベントの種類だけを数えます。入力文字・キーの内容は取得・保存せず、操作も遮断しません。従来の最終入力時刻による判定と異なり、[マウス移動とボタン操作を区別](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)します。編集ワーカー終了時に監視を解除します。

## 入力形式と設定

専用モデルはチャットではなく`create_completion`を使います。ひらがなを全角カタカナにし、以下のマーカーを挿入します。表記は説明用で、実際はそのUnicode文字を送ります。

```text
jinen_v1:   \uEE02左文脈\uEE00カタカナの読み\uEE01
jinen_v2:   \uEE02左文脈\uEE00カタカナの読み\uEE01（全体をNFKC正規化）
zenz_v3_2:  \uEE02左文脈\uEE07右文脈\uEE00カタカナの読み\uEE01
```

空文脈の扱いも形式に合わせます。余分なBOS/EOSを追加せず、temperature=0、反復ペナルティなしで生成します。EOS/`</s>`で停止し、打ち切り・空出力・制御マーカー・空白や改行を含む結果は拒否します。

過去の速度計測はjinen-v2-xsmall / Q5_K_Mで実施しました。現行の既定モデルはzenz-v3.2-xsmallです。以下はjinenへ切り替える場合の設定です。`config.toml`は以下の組み合わせで設定します。smallとxsmall、各GGUF量子化版で同じ形式を使えます。

```toml
model_path = "models/jinen-v2-xsmall-Q5_K_M.gguf"
model_format = "jinen_v2"
```

v2は左文脈が空なら`\uEE02`を省略し、組み立てたプロンプト全体をNFKC正規化して、temperature=0・top_k=1で生成します。正規化するのはモデル入力だけで、元の本文の英数字・記号・対象外の文字は保持します。v1の入力形式は変更しません。仕様は[作者のモデルカード](https://huggingface.co/togatogah/jinen-v2-small.gguf)に従っています。

`config.example.toml`が設定例です。`--config`を省略すると既定値を使用し、`config.toml`は自動読み込みしません。

`backend = "http"`も使用できます。専用モデルは`/v1/completions`、chatは`/v1/chat/completions`を指定します。接続はローカルに限定し、プロキシとリダイレクトを無効化します。`timeout_seconds`はHTTP専用で、直接推論の時間制限はありません。

既存の`config.toml`でも、新しい項目を省略した場合は漢字・「。」が区切りになります。明示する場合は次を追加し、待ち受けプロセスを再起動してください。

```toml
conversion_delimiters = "。"
stop_at_kanji = true
trailing_punctuation = "。、？！?!,.，．"
```

## 対応範囲と検証

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

切り出し、文脈保持、専用マーカー、API呼び出し、応答検証、中止処理を確認します。モデル呼び出し・ウィンドウ操作のモックを含み、実モデルの精度や実アプリでの動作を保証するものではありません。

入力欄の能力だけを確認する場合は、以下を実行して3秒以内に対象の入力欄へフォーカスを移します。モデルを読み込まず、本文を変更せず、本文の内容も表示しません。`backend`、`document_chars`、`selection`、または`unsupported_reason`を表示します。

```cmd
.\.venv\Scripts\python.exe -m kana_rewriter --config config.toml --inspect
```

文字が崩れる場合は、次の起動方法で変換対象・文脈・モデル出力・編集方式を確認できます。診断モードでは対象の文章が端末に表示されます。

```cmd
.\.venv\Scripts\python.exe -m kana_rewriter --config config.toml --debug
```

`時間:`の行には、入力欄の特定、本文と位置の取得、AI呼び出し、キー解放待ち、推論後の再確認、IME一時オフと状態確認、範囲構築、選択反映待ち、送信前確認、SendInput、入力反映確認、カーソル復元、IME復元、編集ワーカーとの往復時間をミリ秒で表示します。途中で中止した工程も`(中止)`付きで記録します。

成功時の`時間集計:`には取得・AI・適用・AI以外・合計を表示します。合計はショートカットの処理開始からIME復元を含む適用完了までです。AI以外は合計からモデル変換呼び出し時間を引いた値です。`全体`や通信時間には内側の工程が含まれるため、工程別の値をすべて足さないでください。診断ログの記録・転送負荷も親工程の時間に含まれます。実アプリで短縮量を測る場合は、同じ入力と設定で比較してください。

速度比較には、本文の診断を省いた`--timings`を使用できます。

```cmd
.\.venv\Scripts\python.exe -m kana_rewriter --config config.toml --timings
```

通常のショートカット実行では、`--debug`と`--timings`のログをメモリーに蓄積し、IME復元と合計時間の確定後に表示します。中止時も蓄積したログを表示します。ワーカーのログも応答と一緒に親へ渡します。ログの記録・整形・転送のコストは残りますが、端末への診断出力は計測終了後です。ワーカーが強制終了した場合、そのリクエストの未転送ログは失われます。`--inspect`と`--text`は即時表示です。

比較用設定`uia_readback_initial_delay_ms`は、UIA文字送信後の初回照会までの休止時間です。0〜100の整数を指定し、既定値は従来どおり0です。0と10などを比較してから採否を判断してください。追加の休止は既存の反映待ち期限内に収め、期待全文・位置・入力先の確認を省略しません。

同じ入力を復元し、各条件30回以上のログを別ファイルへ保存すると、以下で中央値とp95を比較できます。中止件数も表示します。無変換の試行も成功サンプルに含まれるため、必ず元のひらがなに戻して測定してください。

```cmd
.\.venv\Scripts\python.exe -m kana_rewriter --config config.toml --timings > timings-0.log 2>&1
.\.venv\Scripts\python.exe scripts\summarize_timings.py timings-0.log timings-10.log
```

1行目の待ち受けを終了後、設定値を10にして出力先を`timings-10.log`へ変え、同じ手順を繰り返します。試行数が少ないp95は参考値です。時間集計に含まれる「AI以外」で比較し、診断表示が終わるまでの体感時間とは区別してください。

内蔵のUIA/Win32バックエンドでは、推論後の本文・位置確認を置換直前の確認へ集約しました。Chromiumの`auto`判定で中止に使わない未確定範囲の照会は、詳細診断時だけ行います。選択前のIME一時オフ、選択後のIME制御メッセージ禁止、復元、strict判定、送信後の一致確認は維持します。`反映待ち内訳`には、照会・最終確認・休止以外の時間も表示します。UIAの範囲構築はIME一時オフと入力先スレッド同期の後に毎回行います。IME切替前に構築した範囲は、本文が同じでもプロバイダーのアンカーが変わり、`Select()`が実際の選択に反映されない場合があるため再利用しません。範囲は右端を基準に左端を後方へ動かし、文書先頭側のアンカーを引き継がないようにします。選択反映待ちではUIA確認の往復時間を待機に使い、確認直後に追加の固定休止を置きません。期待状態の確認は選択本文・左前方・全文の順で読み、右前方の重複取得を省略します。IME確定（Enter）由来の自動変換では、Enterのキーアップを待たずに適用しますが、本文・フォーカス・IME状態の確認は維持します。

UIAの文字送信後は、本文が期待する全文になるまで本文だけを照会します。反映途中には選択位置・前方範囲の取得を繰り返さず、全文一致後に期待状態専用の本文・選択位置・読み取り前後の整合性確認を行います。文字数だけでは一致と判断しません。照会間隔は最初の3回を1ms、続く3回を2ms、それ以降を5msとし、全体の待機期限は最大2秒です。`反映待ち内訳:`に本文照会の回数と時間、最終確認の回数と時間、実際の休止時間を表示します。ブラウザー側の入力処理そのものにかかる時間は残ります。

入力欄の属性はUIAの`BuildUpdatedCache`でまとめて取得します。編集可否は適用前に新しく取得し、古い状態を再利用しません。一括取得に対応しない入力欄では個別取得へ戻ります。診断用の要素名は取得せず、クラス名とコントロール種別を表示します。

VS Codeで実際のカーソルと異なる`0:0`が取得される場合は、診断の`UIA位置`と`取得`の行を確認してください。空の選択範囲ではTextPattern2.GetCaretRangeを優先し、非対応・非アクティブならGetSelectionを使います。両方が先頭を返す場合は、この経路では実際のカーソルを特定できていません。VS Codeはスクリーンリーダー向けの本文をページ単位で公開するため、UIAの本文がファイル全体と一致するとは限りません。[VS Codeのアクセシビリティ仕様](https://code.visualstudio.com/docs/configure/accessibility/accessibility)

利用者の診断ログでは、`native-edit-context`が本文ではなく「この時点では、エディターにアクセスできません」という案内68文字を公開し、選択位置を`0:0`として返していました。この場合は案内を本文として扱わず、最適化モードの有効化を案内して中止します。VS Codeのエディターにフォーカスを置き、案内にあるShift+Alt+F1でスクリーンリーダー最適化モードを有効にするか、設定で`"editor.accessibilitySupport": "on"`を指定して再確認してください。この設定は本プログラムから自動変更しません。有効化後の部分置換成功はまだ未検証です。カーソル位置を本文の末尾と推定して置換する処理は行いません。

Web入力欄の選択反映は、本文を再取得した文字位置と対象文字列で確認します。中止時には要求した位置と実際の位置を表示し、確認できなかった場合は文字を送信しません。

空行後の行頭やリスト項目の末尾では、UIAの内部的な段落境界によって、左側の文字列が同じでも右へ広げた範囲に余分な改行が入ったり、`Select()`が実際の選択へ反映されなかったりする場合を想定しています。そのため通常経路でも、確認済みの右端から左端を後方へ動かして範囲を作り、対象文字列・開始位置・終了位置・本文の一致を確認します。改行を削って一致扱いにはせず、確認できない範囲は選択・送信しません。この境界の挙動は模擬テストで検証しており、個々の実アプリでの動作確認とは異なります。

本文と範囲の取得中にアプリ側が更新すると、一時的に古い本文と新しい選択位置が混ざることがあります。UIAではこの不一致だけを最大0.5秒、読み取り直して確認します。本文取得の前後でも内容が一致することを確認し、入力後は本文とカーソルの両方が期待値になるまで最大2秒待ちます。文字入力は再送しません。診断の`UIA入力: SendInput送信済み`以降に中止した場合は、すでに文字が変更されている可能性があります。

104文字の本文の`92:104`を12文字の読みから8文字の結果に置換し、本文100文字・カーソル`100:100`を確認する正常系テストを追加しています。範囲を選択する処理と非同期で変化するUIA本文・選択を模擬し、一連の取得・置換・確認を実行します。実ブラウザーへのSendInputの配送と描画は模擬しており、実ブラウザーでの成功を確認したテストではありません。

## TSFによるIME確定後の直接置換

自動変換では、Enter確定時に保持したTSF範囲を編集セッション内で確認・置換する。
UIAによる範囲選択、Unicodeキー送信、IMEの一時オフは自動確定の適用経路には入らない。
手動ショートカットは既存の編集方式を使う。失敗後の方式変更・再送はしない。
詳細は[TSF直接編集の検証と統合](history/TSF_DIRECT_EDIT_TRIAL.md)を参照。
